# Agent Notes

This is a private project.

When changing the codebase, prefer a complete rip-up-and-rewrite with breaking changes when that leads to a cleaner, smaller, more coherent design.

Do not favor incremental edits that preserve legacy structure at the cost of accumulating spaghetti.

Minimalism, clarity, and a single obvious architecture are preferred over compatibility with earlier internal layouts.

No one else works on this project. Always work directly on `main` -- commit and push there, don't create feature branches or PRs.

## Working on the simulator

- The goal is emergent learning; the gates are groundwork. See the README.
- `physics.py` is the whole of how a cell behaves. Keep it small and simple: it is the evidence that the underlying behaviour is simple. Everything else is UI and support.
- Every bundled pattern uses exactly `physics.DEFAULT_PARAMS`, so patterns can be composed on one grid. Don't give a pattern bespoke parameters. If the physics or the parameters change, every pattern must still pass.
- Patterns are generated by `gates.py`; don't hand-edit the JSON files.
- Every time `physics.py`, the shared parameters, or any pattern changes, run `python verify.py` and make it pass before committing. It checks every pattern at ±20% `COUPLING_GAIN` and 30–100 fps (seconds), and learning on random sheets (a few minutes; `python verify.py learning` for just that).
- Derive designs from first principles (README, "Designing Gates From First Principles") rather than blind parameter searches. Measure, and trace failures to a cause before fixing them.
- Before reporting a pattern as working, also check it live: drive the running app through the control channel (`control_in.txt` / `control_out.log`) so the user can watch.
